# 미미르 스코어 API 전환 (2026-11-02)

2026-11-03 동기화 대기 개선: 한 니케씩 계산·저장하던 요청을 약점 속성별 묶음으로 변경했다. 56개 평가 항목을 5회 요청으로 처리하며, 한 요청의 상한은 100건이다. 각 항목의 대상·편성·육성은 그대로 유지한다. 결과는 요청 ID로 연결하므로 응답 순서가 바뀌어도 점수가 섞이지 않고, 한 항목의 입력/계산 오류가 다른 항목의 성공 결과를 버리지 않는다. 순위·프로필 조회는 여전히 저장값만 읽는다. 전체 서버 테스트 42개와 실제 API 묶음 계산 56개 결과가 통과했고, 기존 단건 결과와 전부 일치했다. 로컬 진단에서 외부 API 5회 요청 합계는 약 1.84초였으며 운영 동기화에는 프로필 수집·DB 저장·대기 시간이 추가된다.

2026-11-03 더미 애장품·큐브 정책 수정: 애장품이 있는 더미는 전용 아이템의 최대 3단계(API `favorite_item_lv: 2`)를 적용한다. 없는 더미는 무기별 SR15 소장품을 유지한다. 측정 대상의 소장품·애장품은 실제 육성을 유지한다. 장착 큐브가 있으면 그대로 사용하고, 명시적인 미장착(`harmonyCube: null`)이면 `cubes`에 재장전 큐브(1000303) Lv15를 지정한다. 큐브 정보 자체가 누락된 불완전한 입력은 계속 재동기화를 요구한다. 정책 해시가 바뀌므로 새 조건의 점수끼리만 순위를 비교하며, 기존 DB 점수를 조회 중 재계산하거나 덮어쓰지 않는다.

막대 길이는 `1 - 상위% / 100`. 표본 부족·버전 불일치 시 점수만 표시하고 순위는 집계 중으로 표시한다.
계정·대상·육성·연구실·옵션 정의 변경 시 결과를 지우고 이전 응답도 무시한다.

## 서버와 순위

- `scrapeNikkeProfile`이 프로필 저장과 새 동기화 번호 발급 후 `calculateSyncedScores`를 호출한다. 같은 동기화 번호는 중복 계산하지 않는다. 새 동기화가 시작되면 이전 작업은 새 저장값을 덮어쓸 수 없다.
- `nikke_score_results/{openId}`에 동기화 번호, 처리 상태, `nameCode:weakness`별 점수·딜량·계산 버전·계산 시각·실패 정보를 저장한다. 저장된 점수는 시간 경과나 계산 버전 변경만으로 삭제하거나 재계산하지 않는다.
- `getNikkeScores`와 이전 앱 호환용 `calculateNikkeScore`는 모두 Firebase 인증과 계정 연동을 확인하는 읽기 전용 API다. 후자의 이름이 남아 있어도 실제 계산은 하지 않는다. 클라이언트의 육성·점수 입력은 사용하지 않는다.
- 외부 API에는 임의 UUID와 편성에 필요한 육성·옵션·연구실만 전달한다. 계정 식별정보를 보내지 않는다.
- UTF-8 바이트 단위 Content-Length, 60초 타임아웃, 명시적인 User-Agent를 사용한다.
- Firestore 임대로 동기화 작업 간 API 호출을 직렬화한다. 같은 약점 속성의 항목을 최대 100건씩 묶어 요청하고, 묶음마다 결과를 저장한다. 혼잡 응답은 제한적으로 재시도한다. 실패한 항목은 다음 동기화 때 다시 계산하고 조회·통계 작업에서는 재시도하지 않는다.
- 이전 `nikke_score_cache`는 조회/계산 경로에서 더 이상 사용하지 않는다. 마이그레이션 도구만 현재 육성·정책 해시와 정확히 일치하는 기존 결과를 사용자별 저장소로 복사할 수 있다. 이 과정도 계산 API를 호출하지 않는다.
- `refreshNikkeScoreStatistics`는 5분마다 최대 100개 연동 계정의 저장된 점수만 집계한다. 최근 30일 동기화·동일 동기화 번호·정책·계산 버전의 성공한 결과를 사용하며, 결과가 없는 계정은 계산하지 않고 제외한다.
- 중간 위치를 보존하며 매일 새 전수 집계를 시작한다. 관측된 계산 버전이 바뀌면 예정일을 기다리지 않고 다시 시작한다. 최초 집계는 계정 수에 따라 여러 실행이 필요하다.
- 집계 중 버전 변경 시 해당 세대를 다시 시작한다. 56개 분포는 전수 집계가 끝날 때 한 배치로 교체한다.
- 점수 조회는 계정 단위이며, 저장 결과·분포는 `nameCode:weakness`로 구분한다. 이전 단건 API의 속성 생략 요청은 해당 니케의 첫 등록 속성을 사용한다.
- 같은 니케·속성·정책·계산 버전만 비교한다. 상위 %는 `(더 높은 딜 표본 수 + 같은 딜 표본 수 × 0.5) / 전체 표본 수 × 100`이다. 기존 육성 통계처럼 동점 중간 순위를 적용하고, 반올림 전 딜량으로 비교한다.
- 유효 표본 20명 미만 또는 24시간 지난 분포는 상위 %를 표시하지 않는다.
- `nikke_score_results`, `nikke_score_state`, `nikke_score_cache`, `nikke_score_pages`, `nikke_score_distributions` 컬렉션은 기존 기본 거부 규칙에 따라 Admin SDK만 접근한다.
- 불완전한 과거 저장본은 재동기화를 요구한다. 동기화는 장비 옵션의 원본 function_type/function_value도 저장한다. 알려진 기존 옵션 ID는 검증된 로컬 표로 복원한다.
- 명중률(`StatAccuracyCircle`)과 차지 속도(`StatChargeTime`)는 원본의 음수 값을 허용한다. 원본이 없는 알려진 옵션 ID도 같은 음수 규칙으로 복원한다. 나머지 옵션의 음수나 알 수 없는 옵션은 계속 거부한다. 정상 옵션을 재동기화 오류로 오인하던 문제를 수정했다.

## 운영 반영 순서

2026-11-02 연결 오류 확인 후 서버 반영을 완료했다. 계산 함수가 배포되지 않아 OPTIONS/POST가 404를 반환하던 것이 원인이었다.
Secret Manager에 키를 등록하고 `calculateNikkeScore`, `refreshNikkeScoreStatistics`, `scrapeNikkeProfile`, `getNikkeStatistics`, `getAccountElementDamageStatistics`, `refreshDailyNikkeStatistics`, `refreshNikkeStatisticsNow`를 배포했다.
운영 계산 주소의 OPTIONS 204와 CORS 헤더, 인증 없는 POST의 정상적인 401 JSON 응답을 확인했다. 이 작업에서 웹 프런트엔드는 별도로 배포하지 않았다.
순위는 새 예약 작업의 최초 전수 집계가 끝난 후 표시된다. 과거 저장본의 육성 수집 메타데이터가 부족하면 사용자 계정 새로고침으로 다시 수집해야 한다.

이후 재배포할 때의 순서는 다음과 같다.

1. Secret Manager에 `DILDORO_API_KEY`를 설정한다. 키는 소스·앱 빌드·일반 .env에 넣지 않는다. 로컬 에뮬레이터는 git에서 제외된 `functions/.secret.local`을 사용한다.
2. `calculateNikkeScore`, `getNikkeScores`, `refreshNikkeScoreStatistics`, `scrapeNikkeProfile` 함수를 배포한다.
3. 실제 연동 계정의 재동기화 후 점수 저장, 이후 프로필 조회에서 저장값만 읽는지 확인한다.
4. Flutter 웹을 배포한다. 순위는 첫 전수 집계 완료 후 유효 표본 수에 따라 표시된다.

서버 속성표 변경도 반영하려면 기존 속성별 통계 조회·갱신 함수에 갱신된 `nikkeElements.json`을 배포하고 통계를 다시 집계한다. 이후 니케 원본 데이터를 수정할 때는 `npm --prefix functions run generate:nikke-elements`로 서버 속성표도 함께 갱신한다.

기존 Python/WASM 계산기와 런타임은 조사·롤백 자료로 보존했다. 새 화면은 이 런타임을 호출하지 않는다.
